the purpse of the project is to automate the process of transfering bookeo data into reserve.

## Testing without touching source data

Bookeo is the source system here, so nothing should ever write to it during
testing -- only call its read endpoints (test_connection, get_bookings /
get_all_bookings, get_booking, get_customers, get_customer,
get_availability). bookeo_api.py's create_booking() exists for completeness
but should never be called against the real Bookeo account as part of this
migration.

On the Reserve (SCS Gateway) side, writes are unavoidable since that's the
destination, but SCS gives us three ways to test without polluting real data:

1. QA environment first -- SCSGatewayClient(environment="qa") hits
   qa.reservecloud.com instead of production. Limited uptime and it wipes
   contact info on refresh, so coordinate timing with SCS support and don't
   rely on data persisting there between sessions.
2. mode="test" on every Put Request -- put_request()/BookReservation/
   ReservationUpdate/CancelReservation all accept mode="test" for a
   server-side dry run that validates without applying. Always run test
   mode until every row comes back Created/Merged before ever using
   mode="apply".
3. Temporary Holds for real end-to-end tests -- book_reservation(...,
   temporary_hold=True) / book_temporary_hold() create a reservation that
   blocks inventory but is invisible to SCS users and can only be
   cancelled/converted by this gateway. This is the way to test a full
   booking round-trip (including services, party mix, pricing) without
   creating a reservation a staff member would ever see. Must wrap in
   try/finally and call cancel_reservation() / release_temporary_hold() on
   every exit path -- SCS puts cleanup entirely on us. cleanup.py and
   ReservationsAPI.cancel_all_temporary_holds() exist to sweep any holds
   left behind by a crashed test run; run that sweep after every test batch
   before assuming the environment is clean.

Recommended order for a migration test batch: pull real Bookeo data
(read-only, safe) -> translate it locally -> push to SCS QA if available,
else production with mode="test" -> once test mode is clean, push a small
sample as temporary holds against production -> verify via
get_reservation_service_options()/a Reservation Get Request -> cancel the
holds -> only then consider mode="apply" on real (non-hold) data.

## Does Bookeo data map 1:1 onto Reserve, or does it need cleaning?

Short answer: it needs cleaning, not a straight pass-through. Concrete
mismatches found just from comparing the two clients so far:

- Date/time format: SCS's ReservationCheckAvailability/BookReservation take
  reservationDate as "MM/DD/YYYY" and times as "h:mm AM/PM" (see
  Reserve/main.py's "07/18/2026" / "3:55 AM"). Bookeo's /bookings endpoint
  uses ISO 8601 timestamps ("2026-07-16T00:00:00Z", per the commented
  example in bookeo/main.py). These need explicit conversion, including
  timezone handling since Bookeo's times are UTC and SCS's are presumably
  venue-local.
- Controlled vocabularies vs free text: SCS fields like reservationTypes,
  serviceOptions, requests (asset attributes), specialOccasions,
  cancellationReasons, paymentMethods/paymentTypes are closed lists specific
  to the Alley Cats SCS site -- pulled via
  get_reservation_field_options(site_names=[...]). Bookeo's equivalent
  fields (product/resource names, categories) are whatever was set up in
  Bookeo and won't line up with SCS's option names automatically. A mapping
  table (Bookeo value -> SCS option) needs to be built and validated against
  a fresh get_reservation_field_options() pull -- don't hardcode it, since
  SCS's own docs say these options can change and should be refreshed
  ~daily.
- Party size / asset counts: Bookeo's numberOfPeople vs SCS's partySize
  (sent as a string) and numberOfAssets (int, must be >=2 when set) --
  types and semantics (people vs. physical assets/lanes) aren't the same
  concept and need an explicit rule, not a rename.
- Contact fields: SCS's BookReservation requires firstName/lastName/email/
  mobilePhone as top-level fields; Bookeo customer records may have
  different phone formatting/optional fields -- needs validation/
  normalization before booking or SCS will likely reject or silently
  mis-file it.

  fact.
- No shared identifier: Bookeo's bookingNumber/customerId/productId and
  SCS's confirmationNumber/uniqueId/siteUniqueId are unrelated ID spaces --
  the migration script needs to keep its own
  Bookeo-id -> SCS-confirmationNumber mapping table, SCS won't do that
  correlation for us.

Net: not 1:1. Needs (a) a field-transform layer (date/time split, party
size aggregation, phone/contact normalization), (b) an explicit
Bookeo-value -> SCS-option lookup table built from a fresh
get_reservation_field_options() pull (not hardcoded, since SCS says these
can change), (c) SCS-side admin configuration for reservationTypes/
assetDetailTypes/paymentMethods/paymentTypes before those fields can be
migrated at all, and (d) a dedupe pass on customers before contact import.

## Field-transform script

migration/transform.py implements the mapping table above as pure,
unit-testable functions (split_bookeo_datetime, aggregate_party_size,
pick_mobile_phone, dedupe_customers, format_addons_comment, map_requests,
transform_booking) -- verified against real sample shapes on 2026-08-20.
map_requests() takes an optional `available_requests` list from a fresh
get_reservation_field_options() pull and raises if the static REQUEST_MAP
points at a value SCS doesn't actually have configured, rather than
trusting the map blindly. run_sample() at the bottom of the file is a
read-only demo (pulls 5 real bookings + their customers from Bookeo, real
field options from SCS, prints the transformed rows) -- it makes no writes
to either system.

Still not built: the SCS-side admin config for reservationTypes/
assetDetailTypes/paymentMethods/paymentTypes noted above (that's an SCS
Settings change, not code).

## ID-correlation table

migration/id_map.py implements the Bookeo-bookingNumber <-> SCS-
confirmationNumber correlation table: a JSON-file-backed IdMap class
(id_map.json, gitignored) keyed by Bookeo bookingNumber, storing
confirmationNumber/uniqueId/siteUniqueId/status/bookeo_customer_id/
updated_at. is_migrated(booking_number) is what the push step should check
before booking anything, so a retried/crashed migration run doesn't create
a duplicate SCS reservation for a booking it already pushed.
update_status() tracks a booking through temporary_hold -> booked ->
cancelled; a cancelled entry is_migrated()=False again so a re-run can
legitimately re-push it. Writes are atomic (temp file + os.replace) and
every mutation saves immediately -- verified by killing/reloading a fresh
IdMap mid-test and confirming the entry survived. Also has a CLI
(`python id_map.py list` / `show <booking_number>`) for inspecting the map
without writing a throwaway script each time.

## Push/orchestration script

migration/push.py is the actual write step, and it ONLY writes via
Temporary Holds -- no mode="apply", no permanent bookings, matching the
Testing section's staged approach. Flow per booking: find_reservation_code()
calls check_availability() with the transformed date/time/party_size/
requests and takes the first live SCS slot; push_booking() then calls
book_reservation(..., temporary_hold=True) with transform.py's contact
fields + comments, and records the result in id_map the instant the hold
is created. If that id_map write itself fails, the hold is cancelled
immediately rather than left orphaned with no local record of it --
verified with a fake IdMap.record() that raises, confirming
cancel_reservation() gets called before the error propagates.
push_booking() is idempotent (id_map.is_migrated() short-circuits a
booking that's already been pushed, no duplicate SCS call). Verified
end-to-end against a fake ReservationsAPI (no live calls made building
this): successful push, idempotent re-push skip, no-availability ->
PushError with nothing recorded, record-failure -> hold cancelled, and
cleanup_all_holds() correctly sweeping/cancelling only the live
temporary_hold entries.

CLI: `python push.py push <start_iso> <end_iso> [--limit N]
[--cleanup-after]` pulls real Bookeo bookings in that window (max 31 days,
per Bookeo's own limit) and pushes each as a temp hold;
`python push.py cleanup` sweeps every temporary_hold currently in id_map
regardless of which run created it -- run this after any test batch that
didn't use --cleanup-after.

Caveat: check_availability() only returns currently-open FUTURE slots, so
this can validate the push mechanism against a near-future Bookeo booking
but can't retroactively recreate an already-passed one in SCS.

## Root cause of the 5 failures, found and fixed (2026-08-20)

It was a script bug, not a genuine SCS/Bookeo inventory conflict.
Investigation: all 5 failing bookings were large party packages (King
Pin, The Extreme, Strike & Spare -- party_size 14-20), while every
succeeding JRPYAC-category booking topped out at party_size 12. Live
testing on 08/22/2026 confirmed the exact cutoff: check_availability()
with party_size 10/11/12 returns 50 results, party_size 13+ returns 0 --
with everything else identical. SCS's default (unspecified
number_of_assets) search only auto-combines up to 2 lanes; explicitly
passing number_of_assets=3 for a party of 14 on the same previously-empty
slot returned 10 real results (Lane 3/4/5). Confirmed for all 5: each
needed number_of_assets=3 (party_size 14-15) or 4 (party_size 20) to find
availability that was there all along.

Fixed in migration/push.py's find_reservation_code(): instead of a single
check_availability() call, it now tries the default search first, and if
that comes back empty, retries with number_of_assets=3,4,...,8 until one
finds a slot (raises PushError only if every attempt is empty). Doesn't
hardcode a per-lane capacity number (not a documented SCS setting) --
just searches outward. Verified against a mocked API first (existing
small-party case still resolves in one call, no regression; a
crafted-empty-until-number_of_assets=4 case correctly retries and finds
it; a fully-empty case still raises PushError after exhausting 3-8).

Then re-ran live against the actual 5 previously-failed bookings:
all 5 pushed successfully (ACEB29-ACEB33, using 3-4 lanes each), verified
live, then cancelled and confirmed gone. Combined with the earlier 22,
that's 27/27 real bookings in this window now proven to push successfully
end-to-end, with nothing left held in SCS.

## Pivot to Events pipeline (2026-08-26/27) -- migration target changed

The company doesn't use the SCS Reservations calendar operationally, only
the Events calendar, so the migration target moved off push.py
(Reservations) to a new Events pipeline: migration/push_events.py +
transform.transform_booking_to_event() + a separate id map
(migration/event_id_map.json, gitignored). Key differences from the
Reservations path, all load-bearing:
  - Events have NO Temporary Hold. mode="test" is a server-side dry run
    (creates nothing); mode="apply" creates a REAL, immediately
    staff-visible Event with no verify-then-commit step and no rollback.
    push_events.py defaults every entry point to mode="test".
  - There is no Events availability-check endpoint (nothing like
    ReservationCheckAvailability), so the pipeline cannot detect or avoid
    double-booking the "Bowling Lanes" Location. SCS's own
    maxConcurrentEvents cap on that Location (24) is the only backstop.
  - No Events read/get endpoint in Reserve/events.py either, so
    post-write verification is limited to the mode="apply" response
    (status + eventNumber/uniqueIds). transform.py's EVENT_FUNCTION_TYPE
    is still the hardcoded placeholder "Miscellaneous" -- pushed events
    land under Miscellaneous until an SCS admin creates a Bowling
    Function Type tied to the Bowling Lanes Location.
  - The 40 permanent Reservations from the 2026-08-24 commit run were
    left in place (that calendar is unused, so they're harmless); they
    were NOT migrated to Events or cleaned up. Bookings migrated before
    2026-08-27 therefore exist BOTH as a Reservation and as an Event.

## Idempotency review (2026-08-31): "Option A" tried and REJECTED by the gateway

Concern raised: event_id_map.json is the ONLY thing preventing duplicate
Events on a re-run -- unrecoverable if lost (no Events read endpoint wired
up to rebuild it), race-prone (whole-file rewrite, no lock), and there is
a crash window between create_event() committing server-side and
id_map.record() persisting where a died process => next run re-creates the
Event. User asked for a best-practice fix that doesn't make a local file
load-bearing.

"Option A" attempted: stamp every Event with a deterministic
function.event.uniqueId = uuid5(fixed-namespace, "bookeo:{bookingNumber}")
and let SCS upsert on it (docs: EventFunctionImport response status enum
{Created, Merged, Failed}, "event.uniqueId ... may match input if
pre-specified"). Code was written (transform.event_unique_id_for + field
injection, push_events defensive parsing, tests) then REVERTED after live
mode="test" probes against production disproved it. No data was created --
all probes were mode="test" / read-only.

Probe results (scratchpad verify_idempotency.py + probe.py, 2026-08-31):
  - Synthetic payload WITH function.event.uniqueId set to a fresh uuid5,
    mode="test"  ->  status "Failed", message "No event found for the
    specified uniqueId." So the gateway RECOGNISES the field but treats it
    strictly as a lookup key for an EXISTING event; it will NOT accept a
    client-chosen id to create a new one. Option A is dead on this gateway.
  - Same payload WITHOUT that field, mode="test"  ->  status "Created",
    clean (baseline: the payload is otherwise valid).
  - A REAL already-migrated booking (1577603189305668, Victoria Deaton,
    2026-09-19, SCS event d5026170-... already exists from the 2026-08-27
    run), re-transformed WITHOUT the field, mode="test"  ->  status
    "Created" (NOT "Merged"). So this account has NO native
    duplicate-matching configured for EventFunctionImport -- a re-run with
    no id-map guard genuinely would create duplicate Events (and re-match
    the contact into a new contact.uniqueId).

Where that leaves idempotency: EventFunctionImport is create-only for new
Events; SCS owns the Event id space and does no server-side dedupe here.
The only ways to stop depending on the local file:
  B. Query-before-write. Add a custom/UDF text field to the EventFunction-
     Import header (Settings > Events > Manage Event and Function Gateway
     Put Requests) and store the Bookeo bookingNumber in it on every push;
     configure an Event or Function Gateway GET Request (Settings > Events
     > Manage Function Gateway Get Requests -- filterable, docs show a
     startDate range example) that can filter on that field; before each
     push, GET by bookingNumber and skip if found. Makes SCS the source of
     truth. Needs two SCS admin config changes; no code blocker.
  B-lite. Skip the custom field: configure a Function GET Request filtered
     on function.startDate range, pull the migration window, and match
     already-migrated bookings fuzzily on (startDate + startTime + contact
     email / event name). No schema change, still needs the GET Request +
     a wrapper method. Fuzzy: risks colliding with staff-created events.
  C. EventCreated webhook -> write the mapping to a durable external store
     (hosted KV / DB, not a repo file). Still external state, but robust
     and not a fragile file.
  D. Keep event_id_map.json but make it REBUILDABLE from B's GET Request
     (rebuild_map_from_scs()). Pragmatic minimum -- losing the file stops
     being a data-loss event.

Recommendation: B (or D as a stepping stone). All of them need an SCS
admin to add a GET Request (and, for B, a custom header field) first --
that's the blocker, not the Python.

Meanwhile: event_id_map.json REMAINS the idempotency guard. No code
shipped from this review. The 47 existing entries stay authoritative;
re-running push_events over an already-migrated window is still safe only
because is_migrated() skips those rows.

Unrelated real bug found while here (worth fixing regardless of the above):
push_event_booking() records site_unique_id from uniqueIds.get(

uniqueIds["event.uniqueId"] only in the docs' generic example -- the live
response shape is {"contact.uniqueId","eventNumber","event.uniqueId",

Also the response-parse path (resp["results"][0]) is unguarded -> an

## Migrated events weren't staff-editable -- fixed via agent Ownership Group (2026-09-01)
